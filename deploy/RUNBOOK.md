# Installed agent-messaging operations

The installer owns explicit code and selected integrations, not runtime state. Download the root frontdoor once and run it locally for installation/updates to the latest stable release; use optional Check or an exact Version pin when needed, then separate read-only Verify. The actual OS user and owned operation work directory are automatic. Retained metadata/verifier lives at `<UserRoot>/.agents/installations/agent-messaging`; the ordinary service root remains `<UserRoot>/.agents/services/broker`.

Do not change roots/port or use another account to upgrade. Existing private broker.env, DB/WAL/SHM/journals, logs, audit, credentials, IDs and registrars are preserved. No `.env` is shipped; a fresh installation creates private UTF-8-without-BOM loopback settings from the user's selection.

Code changes while running require separately confirmed `-Activate` on Install. This consent applies only to a process whose absolute entrypoint proves the selected root. A legacy `python server.py` command line does **not** prove cwd/root, even if it owns the selected port and answers health. `-Activate` cannot turn that unknown root into an owned PID. The refusal identifies the observed PID, unproven root, selected InstallRoot and port; it does not stop or change that process.

Before **first adoption** of such a legacy installation, independently inspect its PID/start identity, executable, actual cwd/root and existing registrar/launcher. Confirm those observations belong to the same user's selected installation and port; do not infer cwd from health or a bare argv. With that evidence and separate stop authorization, invoke the existing owned installation's `scripts/stop-broker.ps1 -Port <retained-port>` **without `-Force`**, or use its already established PID-bound operator if its script cannot express that port. Display and retain the observed PID/start/root/selected-port before stopping. If ownership/cwd cannot be established, leave it running and resolve that prerequisite; no mass port kill is authorized. Confirm the selected listener/owned process is gone, then run Check → Install → separate Verify. Known-byte same-user adoption is automatic; a consent flag cannot bypass ownership or drift checks. The new absolute-entrypoint launcher makes later root-bound activation possible; adoption is not a state move.

The frontdoor confirms component/version/PID/root for an eligible activation, uses the installed stop/start operators without Force and checks a new process identity plus database-bound health. Activation failure is separate from installed bytes; never restore a stale database or claim an old healthy listener serves the new code.

Manual commands (use the actual selected root and retained port):

```powershell
& '<InstallRoot>/scripts/stop-broker.ps1' -Port <port>
& '<InstallRoot>/scripts/restart-broker.ps1' -Port <port>
```

Do not pipe/drain detached restart output. For automation, use `Start-Process -PassThru` and wait on the launcher process handle; its descendant inherits pipe handles. Inspect only this installation's logs and PID/root/start identity. `Verify` is intentionally read-only/no-network and is not an activation receipt.

Autostart is preserved, never created by install. Explicit registration is `& '<InstallRoot>/scripts/install-windows-autostart.ps1' -Trigger AtLogon`; existing foreign/variant registrars refuse replacement. Reaper/Discord configuration and enablement are separately authorized optional operations, never normal setup. No receive hooks or organization policy are enabled.

`broker.env` uses one Windows operator/backend grammar: trim the line, skip blank/`#` lines, accept uppercase `KEY` with horizontal whitespace around `=`, trim the value and optional matching outer single/double quotes. `BROKER_PORT` must be a canonical decimal 1–65535 (no sign, leading zeros, inline comment/junk or empty value). Every occurrence is validated before last-valid-wins; an invalid earlier duplicate cannot be hidden. A malformed active port declaration refuses before process queries/writes, even with an explicit `-Port`; that argument must match an existing valid selection. Only a genuinely absent declaration uses the fresh 8787 default. Existing whitespace/quoted declarations are accepted consistently by start/stop/restart, Codex and installer.

On partial failure, retain the returned private WorkRoot backups and diagnostics. File writes are individually atomic, not a whole-install transaction. `operation.json` and `failure.json` include `backup_map` entries mapping each original path to its preserved backup and `kind` (`code`, `configuration`, or `environment`; runtime `state` is not backed up by this installer). Code entries include old/candidate SHA-256 bindings; configuration/environment entries contain paths only, never rendered secret values or their public hashes. Do not retry by deleting unknown state or run an automatic rollback.

After frontdoor handoff, the same resolved WorkRoot is forwarded. Each frontdoor verification pass retains its own `release-*` archive/extraction directory. Backend output reports `work_root`, `operation` (its `operation-*` temp/build directory), and `backups` (the separate `backups-*` recovery directory). Use that exact returned backup path and its `operation.json`/`failure.json`, not a release-extraction directory. Both validation passes' downloads remain retained; the installer does not silently delete them or recovery backups.

Check and a verified no-op return `backups: null` because they created no recovery-backup directory; their reported `operation` still identifies retained temp/build diagnostics. Separate Verify creates neither directory.

For **manual code-only recovery**, first stop only an independently proven owned process with separate authorization. Read the exact operation/failure map and prior installed/source receipt. For each explicitly owned immutable **code** entry, verify the preserved backup's `original_sha256` against the prior trusted bytes; verify the current destination is still the failed candidate's `candidate_sha256` (or expected absent retired file). Drift, unknown effects, incomplete bindings, or changed ownership are a conflict: do not overwrite. A separately reviewed operator may atomically restore only those exact verified code files at their unchanged roots, retaining the failed candidate and diagnostics. This is not a command to restore an entire tree, venv or installation receipt. Do **not** bulk restore configuration, tokens, registrars, environment backups, DB/WAL/SHM/journals, sessions or IDs; never restore an old live SQLite database. Reconcile dependencies/configuration through an explicitly reviewed install after identifying the failure, then run separate Verify; activation remains separately pending until real new-process evidence exists. No automatic rollback or recovery/resume framework is provided.

Metadata/config-only successful reconciliation reports `reconciled`, preserves `last_code_change_utc` when executable/environment code bytes did not change, and does not claim activation. An unchanged verified installation reports `verified-no-op`.
